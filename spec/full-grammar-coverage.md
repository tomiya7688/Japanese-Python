# 基本文法の日本語全面対応要件

状態: **対応範囲と完了条件の確定**。全構文の表記決定・参考実装の完成を意味しない。

## 1. 必須要件

> 基準とするPythonの基本文法を、すべて日本語で書けること。
> Pythonの英語構文も引き続き使えるが、ある構文を使うために英語へ書き戻すことを必須にしない。

ここで基本文法をifやforだけに限定しない。現在の基準である **Python 3.12の言語仕様に含まれる文・式・パターンと、それらの組み合わせ**を対象とする。使用頻度の低さ、専門性、変換器の実装難度を理由に対象外にしない。別のPythonバージョンで追加された文法の対応範囲は、基準バージョンの更新として別途管理する。

「日本語でも書ける」と「英語で書けば使える」は別である。英語のまま通過させる機能は互換機能であり、日本語対応の完了として数えない。

## 2. 既存文書に対する優先順位

**対応範囲・未対応部分の扱い・完了判定については本書を優先する。** [既存構文仕様](JPy-v0.1.md)と過去の文法決定記録にある、以下の対象外方針は撤回する。

- 「文だけを日本語化し、式の表記はPythonの英語のままに固定する」
- 「async/await、yield、lambda、global/nonlocal/del、type、except*、論理演算子・定数等は、日本語表記を追加しない」
- 「複数名・相対・ワイルドカードimport、複数項目のwith等は、英語で書くことを最終仕様として要求する」
- 「括弧内やf-stringの埋め込み式には日本語表記を追加しない」

既存の日本語表記と変換意味は、本書と矛盾しない限り維持する。既存仕様の1項目だけの構文、1行スイートやセミコロンの制限、パターン内部の英語固定等は **現在の対応範囲・制約の記録**であって、全面対応の完成形を定める除外規則ではない。

現状の「文法決定版」は、決定済み部分の記録として読む。全基本文法の完成・全実装済みを表す表題として使用しない。

## 3. 表記と動作を分ける

**式の意味はPythonのまま、表記には日本語を用意する。** 演算子の優先順位、評価順、評価回数、途中で評価を打ち切る動作、名前の扱い、例外、非同期処理、生成器の再開などを変えない。

文頭だけで日本語の語を置き換えて終わりにしない。文の条件、代入の右辺、関数の引数と初期値、型注釈、括弧内、内包表記、lambda、パターンの条件、f-stringの埋め込み式など、対応する構文が合法な位置すべてで使用できる必要がある。

通常の文字列、コメント、f-stringの文字列部分は翻訳しない。f-stringでは文字列部分と式部分を区別し、式部分に日本語表記を認める。式を含む入れ子の書式指定や、デバッグ用の式表示も個別に検証する。CPythonの文脈上の禁止を日本語化によって解除しない。

## 4. 全体を確認する一覧

以下は対象一覧である。Python欄は対応元を示し、日本語の正式表記がすべて決定済みであることを意味しない。細かな文法規則の確認元は末尾の公式文法とする。

| 分野 | 全面対応に含める範囲 | 現時点の整理 |
|---|---|---|
| 条件分岐 | if/elif/else、条件式、各位置の条件式 | 文の表記は決定済み。式としての分岐は追加設計が必要 |
| 繰り返し | for/in、while、else、break、continue、pass | 主要な文は決定済み。式内部や他構文との組み合わせは別途確認 |
| 関数・クラス | def/class、return、デコレーター、全引数形式、継承、型注釈・型パラメーター | 主要な文は決定済み。内側の式の日本語対応も必要 |
| 例外・確認 | try/except/except*/else/finally、raise/from、assert | 基本形は決定済み。except*と原因指定の日本語表記は追加設計が必要 |
| 読み込み | import/from/as、複数名、相対、ワイルドカード、括弧でまとめた指定 | 単一名等は決定済み。制限されている形式も対象に戻す |
| リソース管理 | with/as、複数項目、括弧形式、非同期版 | 単一項目は決定済み。複数項目と非同期版も必要 |
| 非同期 | async def、await、async for、async with、非同期内包表記 | 日本語表記・文法の追加設計が必要 |
| 値を順次渡す処理 | yield、yield from、受け渡し式、通常・非同期の生成器 | 日本語表記・文法の追加設計が必要 |
| 名前・型の宣言 | global、nonlocal、del、typeによる型別名 | 日本語表記・文法の追加設計が必要 |
| 名前なし関数 | lambdaとその引数・本体式 | 日本語表記・文法の追加設計が必要 |
| 値と演算 | True/False/None、and/or/not、in/not in、is/is not、連続比較 | 日本語表記・文法の追加設計が必要。演算の意味は不変 |
| コレクションと式 | リスト・集合・辞書の内包表記、生成器式、入れ子のfor/if/async、アンパック | 記号形式を維持しながら、式内部の英語キーワードに日本語表記が必要 |
| パターン | match/case、ガード、as、値・捕捉・OR・シーケンス・マッピング・クラス・ワイルドカード | 外側の文は決定済み。内部のキーワードも確認する |
| 式が現れる場所 | 代入、呼び出し、属性・添字、スライス、初期値、型注釈、括弧、f-string | 同じ日本語式が文脈に応じて組み合わせられることを検証する |
| 書式・複合形 | インデント、複数行、1行スイート、セミコロンでつなぐ単純文、文字列・数値・bytesの記法 | Pythonの記号・リテラル記法を保ち、組み合わせの対応漏れを残さない |

キーワードの対応表だけでは十分ではない。同じ `if` は文・条件式・内包表記・caseガードに、`for` は文・内包表記・非同期版に現れる。`as`、`from`、`in` 等も文脈ごとに確認する。公式の予約語とsoft keywordの一覧も照合し、単語単位の対応だけで全対応と数えない。

## 5. 日本語化の範囲と、維持する記法

今回の必須要件は **言語構文の英語キーワードを強制しないこと**であり、ソース中の英字をすべてなくすことではない。

- `=`、`:=`、`+`、比較記号、括弧、`:`、`,`、`;`、`.`、`@`、`*`、`**`、`->`、`...`、`_`などの記号はPythonと共通の記法として利用する。記号を日本語の文章へ置き換える必要はない。
- 文字列の接頭記号 `f` / `r` / `b` / `u`、エスケープ、書式指定の記法もPythonと共通の記法として扱う。埋め込む式のキーワードは全面対応の対象である。
- `print`、`input`、`len`、`range`、`int`、モジュール名、属性名、`self`、`__init__`等のAPI・名前は、構文キーワードとは分けて扱う。それらの自動改名やライブラリ翻訳をこの要件だけで導入しない。
- Unicode識別子と日本語構文語との区別を定義し、既存の識別子を無条件に置換しない。日本語と英語の併用も検証対象とする。

## 6. 語の選び方と状態管理

すでに決めた `返す`、`試す`、`例外処理`、`例外を起こす`、`最後に`、`繰り返しを続ける`、`繰り返しをやめる`、`として`と`と名付ける`の併用等は維持する。不要な熟語を避け、動作と対象が分かる言葉を使う。

新しい表記は文法規則・対応するPython・正常例・エラー例を合わせて定義する。適切な語が決まっていないことは「設計未完了」、ツールにないことは「実装未完了」と記録する。どちらも「Pythonで書けるため日本語化は不要」として閉じない。仮の語彙を対応済みの正式構文として紹介しない。

項目ごとに **対象内か、表記決定済みか、変換規則決定済みか、実装済みか、検証済みか** を区別する。対象は本書で確定しており、他の状態が未完了でも対象外へ変更しない。

## 7. 完了条件

全面対応の完了には、以下をすべて必要とする。

1. 基準バージョンの文法規則とキーワードの使用文脈を確認し、英語でしか書けない言語構文が残っていない。
2. 日本語の表記と変換規則が明文化され、式・文・パターンが合法な文脈で組み合わせられる。
3. 日本語のみ・英語のみ・混在のプログラムを、対応するPythonと比較する。通常の結果だけでなく、例外、スコープ、評価順・回数、短絡評価、名前の束縛、遅延・再開、後処理も確認する。
4. 文字列・コメントを壊さず、f-stringの埋め込み式を扱い、診断とソース位置の保証を検証する。不正な構文を勝手に別の意味として受理しない。
5. 単語の置換件数や既存テストの成功だけで全面対応を宣言しない。未実装・未検証の項目を明示する。
6. 同じ言語変換規則を使うcompile/runの両方で確認する。compileはアプリを実行せず通常の.pyを生成し、runは生成.pyを一時ファイルにも書き出さずCPythonで実行する。

言語仕様が主であり、参考変換器の制限に合わせて要件を縮小しない。全面対応要件の確定と、全面対応実装の完成は別である。**この文書の追加はドキュメントのみの変更であり、未実装の構文を使えるようにするものではない。**

## 8. 変更しない契約

英語のPython構文を使う自由、既存の確定表記と互換表記、Pythonの実行意味、独立した通常の.pyの生成、compile/runの役割分離を維持する。PyInstaller/Nuitkaにはcompileで生成した通常の.pyを渡し、runを配布用ビルドの入口にしない。`.jpy`の自動importや独自VM・独自型システムは、本要件に便乗して追加しない。
